# Adapt model and effort within a task

Use this path when the user explicitly delegates model or effort choices for the
current task. A recommendation-only request authorizes advice. Inherit native
settings in ordinary work. Honor each fixed choice independently and use only the
discretion the user granted. Preserve persisted settings, service tier and active
permissions. Adaptive selection does not itself authorize delegation.

## Choose for the remaining work

At the start, assess the acceptance criteria, dependencies, uncertainty, impact
of an error and cost of verification. Prefer direct tools for mechanical checks.
Reassess at a meaningful phase change or when new evidence exposes an unresolved
reasoning problem. Choose effort independently of model. Raise effort only to
address a demonstrated reasoning gap. Resolve missing access, data, or tool
failures at their source. Reuse completed work and passing checks.

On a host that offers them, Sol is a general coding and execution candidate,
Terra can review actual screens when visual judgment matters, and Luna can handle
a bounded, structured text task. Consider Astra for an unresolved problem that
requires deeper judgment. These examples carry no fixed role, effort or speed
policy. Use the active execution tool's exact model and supported effort range.
A catalog on another surface or a bundled list cannot establish availability for
this action. Continue through an authorized native path if a candidate is absent.
If a fixed choice is unavailable, preserve it and report the limitation. Ask for
an alternative only if it blocks required work.

## Apply through native controls

The root owns integration and final verification. Use an authorized new child
only for independent remaining work that justifies coordination. Keep edits and
interactive sessions disjoint. When an override requires a fresh child without
full history, hand off the goal, scope, authority, key evidence and acceptance
check. Use the override only if the active tool supports that exact pair.

Continue the running root turn with its current native settings. Keep an existing
child's settings unless the host exposes a verified control for that execution.
Treat a follow-up prompt as continuation. Reassign only necessary remaining work
if a fresh child is justified and the previous assignment will not duplicate it.

Use a next-turn override only through an available native control with a known
target and authority for that action. A user-visible follow-up message requires
the user's explicit authorization to message that thread. Prefer a separate
authorized thread when the override can affect later turns. For example,
[App Server `turn/start`](https://learn.chatgpt.com/docs/app-server#start-a-turn)
makes its model and effort overrides defaults for later turns on the same thread.

Use a same-thread override only when it is verified to expire with the turn or
when the active interface can read and restore the thread defaults. Before a
persistent override, capture the original model and effort defaults and how to
restore their inheritance if applicable. At the end of the scoped work,
including on early exit, recheck the defaults. Restore the settings still owned
by the override and preserve any newer user choices. Confirm the resulting pair
through native readback before the next unrelated turn. If persistence or
restoration is unknown, use a separate authorized thread or leave the change as
a recommendation and continue with current settings.

## Verify and continue

Verify the work with the task's existing acceptance check. Keep the requested
pair, the pair recorded in the matching native turn, and response-level evidence
of actual model and effort distinct. An accepted request or a child handle
establishes submission. A turn context can retain the initial settings after a
change or provider reroute. Report mismatches and leave response-level settings
unknown when the runtime lacks matching evidence. Use
the acceptance check to establish completion independently.

Keep routing evidence within the task. Use the compact improvement record only
for actual guidance changes and independent later observations. Compare matched
completed outcomes before claiming a quality gain. For cost and speed, include
attributable parent, child and retry resources across that work.
