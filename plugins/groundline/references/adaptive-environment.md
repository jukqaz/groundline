# Improve and align a personal Codex environment

Use this reference for requested usage-driven improvement and environment
alignment. Connect observations, actual delivery outcomes and relevant official
model guidance to a reviewed personal baseline, then verify its next results.
The current release provides audit, delivery, comparison and bounded settings
repair. A persistent learner, baseline synchronizer and environment-receipt CLI
are planned; do not invent their commands or report them as active.

## Establish the requested baseline

Keep the user's explicit preferences separate from learned hypotheses. Identify
the affected host, App/PATH runtimes, active layers, user-owned guidance, skill
sources and relevant plugins. Preserve native resolution and project ownership.
Record only selected evidence and unresolved differences; do not read every
setting, session or reference for an unrelated task.

Use [configuration review](codex-configuration.md) and
[installation alignment](installation-alignment.md) for the actual repair path.
Choose common settings and intentional host exceptions explicitly. Keep private
baselines and backups outside public source. Do not copy credentials, sessions,
databases or provider caches between hosts.

## Learn from work and model changes

1. Reuse relevant [audit](weekly-usage-audit.md) observations and
   [delivery evidence](delivery-evidence.md). Distinguish native completion,
   assistant reporting, checks and user acceptance. Missing results stay unknown.
2. Describe a specific recurring friction or explicit correction and a scoped
   change. Record its basis, expected result and what would invalidate it.
3. Review current official guidance only for the affected model/runtime change
   or demonstrated issue. Retain source URL/date, applicable version and reason.
   Remove outdated instructions when warranted; more rules are not a goal.
4. Preserve explicit model/effort/permission/network choices. A learned
   hypothesis does not authorize replacing them or broadening collection.
5. Apply within the user's existing reversible management scope using native
   file/config tools. Reuse scoped authorization; no confirmation per local step.
6. Verify the affected App/PATH loading and observe later real work. Use
   [outcome comparison](evidence-routing.md) for measured claims; usage aggregates
   alone cannot establish better quality or a best model.

Name the desired baseline revision, written state and verified active state
separately. A successful file update does not reload an existing chat's system
instructions. Plugin installation does not prove hook trust or dispatch.

## Apply and recover precisely

Preview the exact target and diff, save a fresh owner-private backup, reread
before writing and preserve intervening user edits. Modify only requested or
registered files/keys/sections. Never patch managed plugin caches or replace a
whole global AGENTS file to apply one learned rule.

After application, record source and before/after digests, affected host, native
checks and remaining unknowns. Repeated application should be a no-op. Multiple
files or hosts may partially succeed; report and resume per item. Roll back only
when current bytes match the applied state; otherwise prepare a recovery diff
that preserves later edits.

The existing [personal recovery](personal-recovery.md) commands recover old
state only. Do not use retired trial formats for new learning or invent an
automatic migration. Existing config repair does not synchronize all layers.

## Keep the loop useful

Use natural follow-up work to evaluate a change. Record failed attempts, rework,
user intervention and owned parent/child/retry costs. Do not repeat accepted
work or force a benchmark/sample quota merely to populate learning history.
Keep outcome comparisons matched by task, model, runtime and environment basis.
Treat insufficient evidence as observing or inconclusive rather than success.

Research, analysis, instruction loading and environment maintenance also cost
resources. Reuse unchanged evidence and native waitable operations. Use native
automation only for an explicitly requested schedule and defined update scope;
this reference does not create a scheduler or require a per-task audit.
