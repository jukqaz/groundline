# Evaluate quality and resource use

Use representative tasks with the same inputs, acceptance checks, tools, runtime,
service tier and permissions. Hold model/effort and delegation composition fixed
when testing guidance; change the declared factor when testing selection.

Predeclare protected outcomes and the primary resource metric. Assess correctness,
completeness and task-specific quality against acceptance checks, not verbosity
or agreement with a guide. Where human judgment is required, conceal treatment
labels and use consistent criteria. Count rework and failed attempts. Include
root, child, approval and retry resources once; report token components and wall
time separately. Record cache conditions and do not add cached/reasoning subsets
again or turn subscription usage into money.

Use comparable paired cases and counterbalance order when feasible. Report every
attempt, missing evidence, variation and uncertainty. Distinguish a cold-start
comparison from continued work with warm context. Small fixtures prove a code
contract, not model quality or a causal improvement. Avoid replaying real
completed work merely to fill a quota; future authorized tasks can add outcomes.

Use [delivery evidence](delivery-evidence.md) and the single
[evidence comparison](evidence-routing.md). Readiness gates are operational
policies, not confidence intervals. An inconclusive comparison does not block
ordinary native task judgment or authorized bug fixes. GroundLine supplies no
fixed-assumption savings simulator or general person/team maturity score.
