# 주간 점검 증거 완전성 개선 설계

## 목표와 완료 기준

0.25.6에서 해결한 종료 코드 오판과 표준입력 오류를 유지하면서, 실행 중인
검증의 후속 결과를 연결하고 남은 미확정 값의 원인을 수치로 설명한다.
완료 기준은 미확정 값을 억지로 없애는 것이 아니라, 복구 가능한 증거를
복구하고 나머지를 원인별로 남기는 것이다. 사용자 선택 모델·추론·서비스
티어, Chronicle, 원본 기록과 기존 서버 행은 변경하지 않는다.

## 확인한 문제

1. 검증 호출은 `call_id`로 최초 응답만 연결한다. 이후 `wait`와
   `write_stdin`의 별도 호출은 원래 검증에 연결되지 않는다. 스트리밍
   projection이 실행 handle도 버려 후속 결과를 사용할 수 없다.
2. 미확정 개수만 있고 실행 중, 응답 없음, 상태 메타데이터 없음,
   일괄 결과 일부 미확인 등의 이유가 분리돼 있지 않다.
3. 알려진 상속 prefix 제외와 소유권 불명 수집 문제는 나뉘지만, 사용량을
   못 읽은 rollout이 어떤 이유인지 설명하는 분모별 분류가 부족하다.
4. 주간 점검의 LLM 보고서가 완료 턴 128개를 작업 수로 읽거나 혼합 사용량을
   정확한 총량으로 표현했다. App 설치 경로를 제품 표시 이름으로 추정해
   실제 번들 CLI가 없다고 잘못 보고한 사례도 재현했다.

## 구현 범위

### 1. 검증 실행 추적

- 기존 Serde 스트리밍 파서와 표준 문자열 API를 사용한다. JSON은 JSON
  파서로만 해석하며 stdout에서 성공·실패 단어를 검색하지 않는다.
- 원본에 있는 process/session 및 exec-cell handle만 내부 연결 키로 남긴다.
  외부 보고서에는 handle·원문·경로·작업 ID를 내보내지 않는다.
- 같은 rollout 안에서 명시적으로 연결되는 poll만 해당 검증을 갱신한다.
  서로 다른 호출, 프로세스, 작업, 시간 창의 성공을 가져다 쓰지 않는다.
- Oxc AST로 정적 인자의 최상위 순차 호출과 각 출력 위치를 확인한다.
  복수 poll과 조회 결과가 섞여도 출력 개수·순서가 정확히 대응할 때만
  해당 위치를 연결한다. 출력되지 않은 호출은 미확정으로 남긴다.
- 일괄 실행은 모든 필요한 결과가 확인됐을 때만 성공한다. 실패·충돌·
  알 수 없는 출력은 보존하며, 동일 종료 결과는 중복 집계하지 않는다.
- 종료 상태가 없는 결과에는 종료 코드 0을 만들지 않는다. 시점 이후에
  완료된 명령으로 과거 시점의 결과를 변경하지 않는다.

### 2. 관측 가능성의 명시

- 미확정 검증을 응답 부재, 실행 미종료, 상태 부재, 일부 미확인 등으로
  분류하고 분류 합계가 미확정 개수와 항상 일치하도록 한다.
- 사용량 미관측 사유와 현재 지원하지 않는 상속 경계를 구분한다. 원본에
  명시된 소유권 증거가 없는 기록은 추정 복구하거나 삭제하지 않는다.
- Guardian의 미관측 속성과 낮은 표본 커버리지를 정상 값 0으로 표시하지
  않는다. 알려진 범위 제외를 새로운 DB 손상이나 전송 오류로 해석하지 않는다.
- Insights의 현재 ingest 계약과 과거 이벤트는 보존한다. 새 로컬 진단
  필드가 wire 계약을 바꾸지 않는지 회귀 검증한다.

### 3. 주간 점검의 결정적 보고서

- 감사 1회, 동일 결과의 추천 1회를 한 실행 경로로 묶는 옵션을 제공한다.
  기존 감사 JSON과 표준입력 계약은 유지한다.
- 작업 표본 수, 완료 턴, 공급자 보고 사용량의 출처, 사용량 커버리지,
  범위 제외, 실제 수집 문제, 검증 커버리지와 사유를 고정 필드로 제공한다.
- 보고서 문구도 이 필드에서 생성해 작업/턴 혼동과 '정확 사용량' 과장을
  방지한다. 실제 확인하지 않은 설치·훅·서버 상태를 추정하지 않는다.
- App 번들 CLI는 실제 설치 metadata와 실행 파일 존재로 찾는다. 특정
  표시 이름의 앱 폴더 하나만 확인하고 CLI 전용 환경이라고 결론내리지 않는다.
- 기존 주간 자동화에 적용하고 같은 작업에서 재호출해 사람이 보는 최종
  보고서까지 검증한다. 시간 기반 트리거의 검증 여부는 별도로 표시한다.

## 검증 계획

| 경계 | 필수 검증 |
| --- | --- |
| 파서 | 성공/실패/실행 중/상태 없음, 악성 또는 인용된 stdout, JSON·text·batch, 깊이·크기 한도 |
| 연결 | session→poll, cell→wait, 중첩/다중 handle, 결과 중복, 충돌, 다른 rollout, 시간 창 밖 완료 |
| 통계 | 원인 합계와 분모 일치, 누락과 제외 구분, 미측정 null, wire 검증 유지 |
| 보고서 | 14개 작업/128턴 혼동 방지, mixed 출처 문구, 1회 감사, 추천 실패 보존, 출력 비밀값 미포함 |
| 실제 기록 | 고정 UTC 창의 구버전/수정본 비교, 원본·사용량·수집 커서 불변, 미확정 원인표 |
| 릴리스 | 관련 crate 테스트, workspace/소스/개인정보/의존성 검사, CI, 배포 산출물 checksum·attestation |
| 설치·운영 | 두 설치본 무결성, NAS health/버전, 실제 훅→ACK→DB 일치, 과거 행 보존, 주간 작업 재호출 |

## Astra 효과의 해석

이번 작업은 잘못된 판단과 중복 감사를 줄이는 GroundLine의 정확성을
검증한다. Astra 자체의 성능 향상이나 비용 절감을 자동으로 주장하지 않는다.
효과 비교는 같은 업무·완료 조건·사용량 출처·검증 커버리지를 갖춘 자료로만
하며, 완료율과 재작업을 확인할 수 없는 집계에서는 설정 변경을 권하지 않는다.
현재 명확한 결함의 수정에 새로운 모델 실험이나 글로벌 설정 변경은 필요 없다.

## 배포와 복구

검증된 새 patch 버전을 공개 배포하고 현재 Mac의 Core/Insights와 NAS API에
적용한다. NAS의 다른 이미지·볼륨·인증·네트워크는 유지한다. 배포 전후 행을
비교하고 release digest와 설치 hash를 기록한다. 문제가 생기면 보존된 직전
API digest와 공개 패키지로 복구하며 데이터 reset이나 Git 이력 재작성은 하지 않는다.
